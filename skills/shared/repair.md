# Interruption and repair

On a lost native response, inspect the affected bead and assignee before retrying. If another actor owns it, do not edit. If it names this thread, reconcile existing tools and work first. An unchanged record alone does not prove an older request cannot still complete; resolve the client/provider operation.

Stop relevant damage, identify affected writers and native operations, inspect worktree, candidate and Beads state, preserve explicit pauses, and use native commands for repair. Reassign only after prior writers and external work are settled. Otherwise leave the assignment for investigation. Coordinate exceptional server maintenance with shared users. Other beads remain available through native atomic claiming; there is no Hive-wide write barrier.

## Choosing a resolution

Justiciar decides. When an incident has several possible resolutions, choose the correct one and implement it; do not present recovery options to the user. Involve the user only for an explicit pause, a required approval, or access you lack. A requirement whose authority is unclear stays in force and is not relaxed; when it alone blocks progress, treat the one decision it needs as a required approval and ask for exactly that.

Contain the damage through the affected tool's supported recovery. When Hive or Tollgate offers none, fix the defect in that tool rather than editing its state by hand or waiting. Tools owned by other parties, such as Beads or Dolt, remain external dependencies even with a local clone: record the concrete unblocking action and the party who must take it.

A defect in Hive or Tollgate is not an external dependency. File its fix as its own bead, in the tool's registered project or with the missing registration reported under [filing](filing.md); the recovering thread claims and implements that bead itself even without `hive_project`, as an exception to the one-assignment guidance and to recovery not being a separate assignment. Implement it under that repository's `AGENTS.md`, including its promotion approvals and coordinated restarts of shared services. This recovery mandate is the cross-project authorization [entry](entry.md) requires for that fix, even where the blocked project otherwise restricts work in other repositories; record that exception on both beads. The blocked bead stays claimed, with a recorded checkpoint and a dependency edge on the fix bead. When the defect also blocks the tool's own delivery path, the user's explicit authorization for an emergency bypass, such as working on master, is the required approval to ask for; record the bypass.

## Executor recovery before stopping

Before a perceived blocker, retry cutoff, timing miss or resource pressure can end authorized executor work, invoke the justiciar skill in the same task, without delegating implementation or releasing the bead. An identical retry limit ends those retries, not useful diagnosis or repair. Explicit user pauses and unapproved designs remain immediate holds; recovery never overrides them.

Apply the [temporary justiciar title](entry.md#temporary-justiciar-title) before recovery: replace the current role emoji with 🔥, keep it while justiciar powers apply, and restore the executor title when returning to execution or the appropriate exit title when recovery ends.

Inspect the actual failure and its evidence, current acceptance, worktree, native candidate, assignments, outstanding writers and provider outcomes. Identify the constraint's source and authority. Repair within the existing scope; you may relax an agent-created budget, workflow retry rule or self-imposed implementation requirement when that remains within user authorization. Record the old requirement, its source, replacement, justification and consequences on the bead, together with checks still owed. Do not silently waive explicit user acceptance, required approval, access controls or project invariants, invent successful evidence, or broaden scope. If a requirement's authority is unclear, preserve it while continuing independent diagnosis. Choose and implement the resolution under [choosing a resolution](#choosing-a-resolution).

After a repair or authorized relaxation, return to executor, explicitly re-enter its Codex opt-in if disarmed, and resume implementation or acceptance on the owned bead. Recovery is not a separate implementation assignment. If a true external dependency or capacity limit remains beyond available authority (a Hive or Tollgate defect is not one), record attempted recovery, concrete evidence, the party/action needed to unblock, and the safe checkpoint. Settle writers and delivery before releasing ownership; any deferral additionally requires the independent decision below. Then inspect independent eligible work in the project queue, unless the user explicitly limited the request to named work. Do not repeat unchanged attempts or force infinite continuation. If useful authorized work remains possible, continue it.

Only after that inspection may an unresolved blocker or pressure end execution: use `hive executor stop --kind blocked` or `--kind pressure`, with both `--reason` and `--recovery` containing the evidence above. The command requires a recovery account but cannot verify the role transition, its adequacy, or truthful classification. Other stop kinds are `pause` (explicit user instruction), `approval` (required approval outstanding), `drained` (no eligible work), and `scope` (the user explicitly limited the request to named work that is complete or unavailable); these must not disguise a recoverable impediment. All stops still require a concrete `--reason`.

## Deferral decisions

Deferral has an extremely high bar. Before creating a bead as `deferred`, changing an existing bead to `deferred`, or setting/extending a deferral date, obtain explicit agreement from a **fresh justiciar subagent** for that exact proposal. Invoking justiciar in the executor's own context, a cold code review, silence, or an earlier agreement is not a substitute. This applies to every role, including initial Weaver approval holds, and is a workflow requirement rather than a Beads-enforced gate.

Keep authorized work actionable. Ordinary prerequisites belong in native dependency edges; missing evidence, a failed check, elapsed time, capacity pressure, optional feedback and an agent-invented sign-off do not by themselves justify deferral. Approval of a plan authorizes its implementation and verification without intermediate approval holds. Check the latest user direction against the claimed hold: an obsolete request for approval is not a present blocker. A defensible deferral needs a current explicit user pause/required approval or an unavoidable external action, with no useful authorized path to advance that bead after reasonable recovery.

Spawn a new reviewer with no inherited author conversation, instruct it to use the [justiciar skill](../justiciar/SKILL.md), and supply the exact bead IDs or proposed filings, current native state, relevant user instructions with their chronology, requirement sources, attempted recovery and alternatives, outstanding writers/delivery, and proposed resumption condition. It investigates read-only and returns agree/disagree with evidence; it neither claims nor implements the work, and does not recursively request another deferral reviewer. One proposal may cover a named epic and children sharing the same hold, but agreement must explicitly cover every bead. Changed reasons or additional beads require a fresh review.

Before dispatch, the invoking task's owner applies the [temporary justiciar title](entry.md#temporary-justiciar-title), retaining 🔥 until the justiciar decision ends and then restoring the appropriate title. The reviewer follows the same rule for its own task when the host exposes a separate title; title changes are the UI-only exception to this review's read-only scope.

Before the native deferral write, record the reviewer's identity, explicit agreement and reasoning, the concrete remaining action and responsible party, and the condition that resumes work in each bead's notes. For initial filing, obtain agreement first and include that record when creating the bead, or finish the record on an open bead without `hive_project` before deferring and publishing it. A stop record is not deferral approval. If the reviewer disagrees or is unavailable, do not defer; continue authorized recovery or record the unresolved review without claiming that user input is required. Never bypass this requirement by permanently hiding work from project readiness instead.

Honor explicit user pauses and genuinely unapproved scope immediately while review is pending; review is required for the Beads state change, not permission to respect the user. Keep unapproved new filings out of the selectable project list until their hold is resolved. On resumption, compare the recorded condition with the latest authorization, remove superseded holds through native updates, and preserve real dependency edges. Do not ask the user to approve the same work again merely because an old bead still says `deferred`.
