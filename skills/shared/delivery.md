# Native delivery

Claim before substantive work; follow-up work after a close gets a new bead rather than a reopen. After an acknowledged native claim, create a Tollgate worktree with `tg worktree create NAME --json`; it bases the worktree on the gated `staging` tip. Implement within scope, run the configured project's required validation and relevant focused checks, then commit with a Conventional Commit message. Resolve commands from that project's `AGENTS.md` and executable validation configuration, honoring setup, staged-input and selected aggregate requirements. Use a fast-check script only where that project defines it; focused checks do not replace required aggregate validation or native candidate certification. Apply the [executor review policy](../executor/SKILL.md) to decide whether to schedule review. When required, request a fresh cold 🛡️ warden subagent with no inherited conversation (a Codex subagent, or a Claude Code Agent-tool subagent told to use the warden skill). Give it scope, diff/base/source, workspace, invariants and checks. Address substantive findings and review source-changing fixes within that review.

Submit with `tg candidate HEAD --json`, approve with `tg approve ID --wait --json` and inspect/wait with `tg status ID --json` or `tg wait ID --json`. Run waits from a durable project directory; promotion may remove a clean worktree. Settle workspace-rooted background writers first. Keep the bead assigned through review, CI, provider draining and uncertain outcomes. A cancelled observation client does not prove provider work stopped.

Confirm the exact candidate, tested integration result and promotion to `staging`; promotion to `staging` is landed work. `tg status --json` reports both Tollgate refs and the release lag. Record the `release` lag and release state from `tg release status --json` with the delivery outcome. A repository without release-stage steps moves `staging` and `release` together, so promotion also covers `release` and any configured remote push; with release-stage steps the configured remote follows `release`, which a passing release run advances after promotion. Wait with `tg wait --released ID --json` only when the user requires the work to be live or published. Local master is user-owned and follows the repository's `sync_user_master` setting (`staging` by default); its lag or a needs-attention synchronization never undoes promotion. Only then record completed outcome and close the bead. Handle in-scope CI/conflict failures on the same bead; unknown delivery remains assigned for investigation.

Fix a failing release run forward with a follow-up commit in a new candidate (under a new bead once the original is closed), never by rerunning it until it passes; `tg release retry` allows at most one rerun for a stated flaky-step hypothesis. When `promotion_pause` reports `release-lag` (`max_release_lag`), authorize the candidate that repairs the red release with `tg approve --release-fix ID --wait --json`. Report a pause that your own candidate did not cause as its blocker instead of marking that candidate a release fix.
